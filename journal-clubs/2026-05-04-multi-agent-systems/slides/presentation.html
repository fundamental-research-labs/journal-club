When Multi-Agent Helps
and When It Doesn't

A Survey of 11 Recent Papers

Journal Club · May 2026

11 papers from the last 6 months. The goal: build an empirical decision framework for when multi-agent coordination is worth the overhead.

The Thesis

Multi-agent LLM systems promise division of labor, parallelism, and diverse perspectives.

But across 11 recent papers, a sharper picture emerges:

Multi-agent helps for decomposable, verifiable, isolated tasks.
For everything else, the overhead usually isn't worth it — and may make things worse.

This talk walks through the evidence: where multi-agent wins, where it loses,
why scaling agents hits a wall, and what architectural patterns survive.

Act I

The strongest positive case for multi-agent

CAID: Branch-and-Merge Coordination (Geng & Neubig, CMU)

  • Manager builds dependency graph of the repo
  • Engineers work in isolated git worktrees — physical separation, not prompt-based
  • Integration only via git merge, gated by passing tests
  • Structured JSON task specs — no free-form dialogue between agents

Key design choice: borrow coordination primitives from human software engineering (branches, merges, test suites) rather than inventing agent-specific protocols.

CAID: The Numbers

Consistent gains across models and benchmarks:

  • +6.1pp PaperBench with Claude 4.5
  • +6.0pp Commit0-Lite with Claude 4.5
  • +14.7pp Commit0-Lite with MiniMax 2.5
  • Worktree isolation (63.3%) beats soft isolation (55.5%) on PaperBench
  • Doubling single-agent iterations gives marginal gains; CAID's are 2–4× larger
  • But: diminishing returns at N=8 engineers — optimal is 2–4

Score gain from CAID vs. doubling single-agent iterations

Why It Works: Delegation Shapes the Trajectory

Same repo (minitorch), two CAID runs. Run 2 assigns autodiff.py — a critical dependency — and achieves 34.3% vs 8.7%. The bottleneck is the manager's delegation intelligence: identifying high-impact files, not just distributing work evenly.

Act II

The counter-evidence: when multi-agent fails or is illusory

CooperBench: Cooperation Collapses Without Isolation (Khatua et al., Stanford/SAP)

  • 652 tasks: 2 agents implement potentially conflicting features on the same repo
  • GPT-5 / Claude Sonnet 4.5: ~25% success
  • That's 50% below a single agent doing both features sequentially

Root causes

  • Jammed channels — vague, ill-timed, repetitive messages
  • Commitment deviation — agents agree on a plan, then do something else
  • Broken expectations — wrong mental models of what the other agent is doing

The bottleneck isn't coding ability — it's social intelligence. CAID avoids this entirely by eliminating inter-agent dialogue.

Two agents work on conflicting features with potential merge conflicts

Are Multi-Agent Gains Just More Tokens? (Tran & Kiela)

The argument

  • Multi-agent uses more tokens: role prompts, inter-agent messages, coordination overhead
  • A fair comparison must equalize thinking-token budgets
  • Their "SAS-L" variant: single agent with longer thinking — same total tokens as multi-agent

The result

  • Across Qwen3, DeepSeek-R1, Gemini 2.5: single agent matches or beats multi-agent at every token budget
  • SAS is the strongest architecture in 72% of (model, budget) configurations
  • Multi-agent overhead destroys information — tokens spent on coordination are tokens not spent on reasoning

SAS vs. multi-agent under matched thinking-token budgets

Critical methodological point: most multi-agent papers do NOT equalize compute. This is on multi-hop reasoning tasks specifically, not SWE tasks like CAID targets.

Act III

When does adding agents help? The scaling laws

A Science of Scaling Agent Systems (Kim et al., UW/Microsoft/MIT)

Methodology

  • 260 configurations: 5 architectures × 6 agentic benchmarks × 3 LLM families
  • Architectures: single, parallel voting, sequential debate, centralized orchestration, hierarchical
  • Benchmarks chosen for genuine agentic tasks (SWE-bench, WorkBench, PlanCraft...) — not GSM8K

The threshold effect

  • Coordination helps below a single-agent performance threshold
  • Above the threshold, coordination adds overhead without benefit
  • Success depends on alignment between coordination topology and task structure

6 agentic benchmarks spanning SWE, planning, and tool-use

This explains CAID's pattern: large gains with weaker MiniMax 2.5 (+14.7pp), smaller with stronger Claude 4.5 (+6.0pp). Multi-agent is most valuable when individual agents aren't good enough alone.

Diversity, Not Scale (Yang et al., SJTU/Caltech/CMU)

Information-theoretic framework

  • Performance bounded by effective info channels K*, not agent count
  • Homogeneous agents = correlated outputs = redundant channels
  • Residual error decays as e-αK where α = complementarity rate

The headline result

  • 2 diverse agents = 16 homogeneous
  • 4-layer isolation: L1 (identical) → L2 (persona) → L3 (model) → L4 (full diversity)
  • Only correct-path diversity helps — not all disagreement is useful

Caveat: tested on 7B-8B open models (Qwen, Llama, Mistral) with Vote/Debate on GSM8K/ARC. Unclear if this holds for frontier models or SWE tasks.

Heatmaps: rows = diversity layers (L1–L4), columns = N agents. Green → red = low → high accuracy.

Act IV

The deeper problem: degradation and the epistemic gap

Code Quality Erodes Over Time (SlopCodeBench, Orlanski et al.)

Benchmark design

  • 20 iterative problems, 93 checkpoints — agent extends its own prior code
  • Black-box specs only: no prescribed internals, no visible test suite
  • Tracks structural erosion (complexity concentration) and verbosity (redundant code)

Findings across 11 models

  • No agent solves any problem end-to-end (0/20)
  • Erosion rises in 80% of trajectories, verbosity in 89.8%
  • Agent code is 2.2× more verbose than human code — and the gap widens over time

Erosion and verbosity climb monotonically across 6 models (3 per provider)

Prompts Shift the Intercept, Not the Slope

  • anti_slop: forbids verbose patterns, defensive over-engineering
  • plan_first: requires planning before coding
  • Both reduce initial verbosity and erosion — a cleaner starting point
  • But the degradation slope is identical to the baseline
  • Compounding resumes at the same rate regardless of prompt

Degradation is structural — a property of how LLMs modify code under iteration, not a prompting failure. Multi-agent doesn't solve this; it may compound it through coordination overhead.

anti_slop and plan_first shift starting quality but track baseline slope exactly

Documents Degrade Across 52 Domains (DELEGATE-52, Laban et al., MSR)

Method: backtranslation relay

  • Each edit task is reversible (forward + backward instruction)
  • Chain 10 round-trips = 20 delegated interactions
  • Measure semantic similarity to original document after the relay
  • 52 domains: code, crystallography, music notation, recipes, genealogy...

Results

  • Average 50% degradation across all models by interaction 20
  • Even frontier models (GPT 5.4, Claude Opus): ~25% loss
  • Python is the only domain where most models are lossless
  • Tool use makes it worse (6% additional degradation)

Degradation table: all models accumulate errors, background color = deviation from seed

The Domain Heatmap: Almost Nothing Is Ready

✓ = "ready" (RS@20 ≥ 98%). Python is the only domain where a majority of models pass. Sparse critical failures (≥10pt drops) explain ~80% of total degradation — models don't die by a thousand cuts, they have occasional catastrophic errors that compound.

The Epistemic Gap: Scaffold ≈ 1.5% of Variance (Ríos-García et al.)

Methodology

  • 25,000+ agent runs, 8 scientific domains, 3 models, 2 scaffolds (ReAct + Tool Calling)
  • Factor agent as πoverall = f(πLLM, πscaffold)
  • IRT to separate knowledge vs. reasoning abilities
  • Bayesian latent-factor model predicts task success

Variance decomposition

  • Reasoning: 41.4%
  • Env × scope: 30.1%
  • Scaffold: 1.5%
  • Verbosity: 0.1%

Figure 3: Variance decomposition — reasoning dominates, scaffold is noise

Agents Execute Workflows but Don't Reason

Epistemological trace analysis

  • Each step classified as: Hypothesis, Test, Evidence, Judgment, Update, Commit
  • Graph structure reveals reasoning patterns (or their absence)

The breakdown rates

  • Evidence ignored in 68% of traces
  • Refutation-driven belief revision: only 26%
  • Convergent multi-test evidence: 7%
  • Same topology regardless of task type — no adaptation to epistemic demands

If the base model can't reason epistemically, no amount of multi-agent scaffolding will produce reliable scientific inquiry.

Figure 4: Reasoning breakdowns dominate productive patterns in all domain groups

14 Ways Multi-Agent Systems Fail (Cemri et al., NeurIPS 2025 Spotlight)

MAST taxonomy from 1,600+ traces

  • System design: wrong tool selection, poor decomposition, missing capabilities
  • Inter-agent misalignment: contradictory outputs, role confusion, communication breakdown
  • Task verification: no self-check, wrong success criteria, silent failures
  • 7 MAS frameworks, 5 LLMs, inter-annotator κ = 0.88
  • CEO workflow adjustment (+9.4% success) from MAST-guided interventions — but the authors note isolated fixes are insufficient

CAID's design addresses misalignment (structured JSON, no dialogue) and verification (test-gated merging) — but system design failures (poor decomposition) remain the manager's bottleneck.

MAST-Data pipeline: trace collection → failure annotation → taxonomy

Act V

Architectural responses: what works

MaAS: The Right Topology Varies Per Query (Zhang et al., ICML 2025 Oral)

Treat topology as a NAS problem

  • Agentic Supernet: continuous distribution over agent configurations
  • Controller samples a query-dependent architecture at inference time
  • Easy queries → fewer agents; hard queries → more agents, different routing

Results

  • 6–45% cost of hand-crafted baselines
  • +0.5–11.8% accuracy across 6 benchmarks
  • Transfers across LLM backbones without re-training

If scaffold is only 1.5% of variance with fixed topologies, maybe the issue is that fixed topologies average out. Adaptive selection could be the missing piece.

MaAS framework: controller samples from agentic supernet per query

MemMA: Self-Healing Memory (Lin et al., Penn State/Amazon/Microsoft)

The memory cycle problem

  • Construction → Retrieval → Utilization are coupled, not isolated
  • A bad write during construction propagates to retrieval and answering
  • Feedback is sparse and delayed — you only know a write was bad when a downstream question fails

The "immune system" approach

  • Forward path: Meta-Thinker guides what to store/consolidate/resolve
  • Backward path: synthesize probe QA → verify memory → repair failures in-situ
  • Outperforms all baselines on LoCoMo; improves 3 different storage backends

The only architecture in our survey designed to combat horizon degradation. If SlopCodeBench and DELEGATE-52 show degradation is structural, MemMA suggests the mitigation is architectural self-repair, not better prompts.

MemMA: forward (construction + retrieval) and backward (probe → verify → repair) paths

Synthesis

A decision framework from 11 papers

When Multi-Agent Helps

1
Task has natural decomposition boundaries — CAID: file-level deps, test-per-module
2
Subtasks are independently verifiable — CAID: test suites gate each merge
3
Physical isolation prevents interference — git worktree > soft context separation
4
Agents are diverse — Yang et al.: model + persona diversity; 2 diverse ≈ 16 homogeneous
5
Single-agent baseline hasn't already saturated — Kim et al.: threshold effect; weaker models benefit more

Software engineering with explicit repo structure, test suites, and git isolation is the sweet spot. All five conditions are naturally met.

When Multi-Agent Hurts

1
Tasks require tight real-time coordination — CooperBench: communication overhead dominates
2
Homogeneous agents on reasoning tasks — Yang et al.: K* ≈ 1, redundant channels
3
Compute isn't controlled for — Tran & Kiela: multi-agent "gains" are often just more tokens
4
Long-horizon without self-repair — SlopCodeBench + DELEGATE-52: degradation is structural
5
The base model is already strong enough — Kim et al.: above threshold, coordination = pure overhead

The Uncomfortable Takeaway

  • Multi-agent works for decomposable, verifiable, isolated tasks — SWE is the sweet spot
  • For reasoning, coordination, and long-horizon quality: multi-agent is usually not the answer
  • The bottleneck is the base model (41.4%), not the scaffold (1.5%)
  • Degradation is structural and compounds — monitor-and-repair (MemMA) may be the only viable mitigation
  • Diversity matters more than scale — but the evidence is only on small models
  • Adaptive topology (MaAS) could reconcile fixed-scaffold's poor showing — but remains untested on frontier-model agentic tasks

Open Questions

1
If scaffold ≈ 1.5% of variance, what is the value of multi-agent frameworks?
Or is the problem that fixed topologies average out, and adaptive selection (MaAS) would change the picture?
2
Does diversity-over-scale (Yang et al.) hold for frontier models?
7B models are already weak individually — frontier models may not need diverse "opinions"
3
Is social intelligence trainable, or must we design it away?
CooperBench vs. CAID: eliminate dialogue (engineering) vs. make dialogue work (training)?
4
Can we stop degradation, or only detect and repair it?
SlopCodeBench: prompts shift intercept, not slope. MemMA: repair after the fact. Is there a third option?
5
What's the right evaluation methodology for multi-agent?
Must we always equalize token budgets (Tran & Kiela)? Or is wall-clock time the right metric?
