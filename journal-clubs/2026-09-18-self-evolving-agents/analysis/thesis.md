# Self-evolving agents: when experience helps with the next task

## Learning that lasts

An agent fails at a task, records what went wrong, and tries again. Another agent writes a useful program and saves it for a future job. Both have learned something from experience. But they leave us with different questions: can the first agent fix this mistake, and can the second use what it learned somewhere else? Early systems made these possibilities concrete. Reflexion stores written feedback to guide later attempts; Voyager builds a library of executable skills as it explores. The distinction matters because success on a retry does not, by itself, show that an agent has become better at new work. [Reflexion, §§3–4](https://arxiv.org/abs/2303.11366v4); [Voyager, §§2–3](https://arxiv.org/abs/2305.16291).

For this journal club, *self-evolution* means that an agent's experience changes something it keeps and uses later. That might be a memory, a set of instructions, a program, or the model's weights—the numerical parameters changed during training. “Self” does not mean the system does everything alone. People may still supply its feedback, set its goals, and write the rule that decides which changes survive. To understand a system, we need to know both what the agent can change and what remains outside its control. [SEAL, §3](https://arxiv.org/abs/2506.10943v2); [STOP, §3 and Algorithm 1](https://arxiv.org/abs/2310.02304v3).

The research supports a clear but limited conclusion: agents can turn experience into useful changes in the settings tested so far. Whether those changes keep helping on new work, and whether they justify their cost, is less certain. Some experiments find that agents perform better when they keep what they have learned. Others find that much of the gain can be matched by giving the agent a good fixed procedure or more attempts. The central test is therefore what happens after learning: does the changed agent do better on future work than these alternatives, without losing earlier abilities or spending too much to improve?

## What an agent can change

One way to learn is to keep better records. The underlying model stays the same, but it can consult lessons or reuse programs from earlier tasks. WikiSkill takes this idea a step further by separating accumulated knowledge from the skills selected for use. If a proposed skill edit fails, the system can reject the edit while keeping what it learned from the attempt. In its experiments, Qwen-3.5-9B's average accuracy across five benchmarks rises from 29.9% to 47.4%. Each benchmark receives equal weight in that average, and the study reports three evolution runs using separate development and test data. The gain is encouraging, but the setup makes some parts of the problem easier: the agent receives skills directly, rather than having to find the right ones, and the validation sets used to select changes are small. A smaller model also gets worse on OfficeQA. [WikiSkill, §§3–4, Table 1 and Appendix B](https://arxiv.org/abs/2608.27454v1).

An agent can also change the instructions and software that organize its work, often called its *harness*. GEPA examines records of an agent's actions and results, proposes revised prompts, and keeps candidates that work well on different examples. Here, the lesson becomes part of the instructions for future work. SEAL takes a different route: it trains a model to write the data and instructions used to update its own weights. In an experiment where the model learns from one passage at a time, SEAL reaches 47.0% accuracy, compared with 39.7% when the model generates training data without first learning how to do so. The evaluation covers 974 questions from 200 passages held out of training. This shows that a model can learn to produce more useful training material in that setting. It does not tell us whether changing weights is generally better than changing prompts; the studies use different tasks and budgets. [GEPA, Algorithm 1 and §4](https://arxiv.org/abs/2507.19457v2); [SEAL, Table 2 and Appendix B](https://arxiv.org/abs/2506.10943v2).

A more ambitious goal is to improve how the system learns. R-Zero pairs a model that invents problems with a model that learns to solve them, allowing the training problems to change as learning proceeds. STOP and Hyperagents let the system edit the code that proposes improvements. Dream-RSI uses records of earlier searches to revise a controller that decides what to explore next. These methods raise a further question: can an agent learn a better way to improve, then carry that method into a new setting? Finding a better solution to one problem is only part of the evidence needed. This ambition also predates the latest papers: STOP was already editing improvement code in 2023. [R-Zero, §2](https://arxiv.org/abs/2508.05004v4); [STOP, Algorithm 1](https://arxiv.org/abs/2310.02304v3); [Hyperagents, §3](https://arxiv.org/abs/2603.19461v1); [Dream-RSI, §3](https://arxiv.org/html/2609.14858v1).

In practice, a system can combine several of these methods. Shopify's August 2026 account of Sidekick describes a process that revises the harness, repairs unsuccessful sequences of actions, trains model weights, and compresses prompts. It shows how a production system can turn failures into changes at several levels. The article does not, however, report experiments that separate each step's contribution or track quality over successive learning cycles. It gives us a concrete design to study, while leaving the benefit of continual learning itself difficult to measure. [Shopify Engineering, “Sidekick's continual learning loop”](https://shopify.engineering/sidekicks-continual-learning-loop).

## How much of the gain comes from learning?

A useful first test is to let one agent keep its experience and make another start fresh each time. FinEvo-Bench does this with four agent software frameworks, all using the same underlying model. Each processes 120 financial tasks in three shuffled orders. Keeping experience raises average scores by 9.33–19.37 points on the benchmark's grading rubrics compared with resetting the agent. These are gains on recurring professional procedures, where lessons from one case can help with another. The paper does not provide uncertainty intervals across runs for these main effects. [FinEvo-Bench, §§4.1–4.3 and Table 3](https://arxiv.org/html/2608.06144v1).

But starting fresh without useful guidance may be an undemanding comparison. In a separate FinEvo test using one framework, an agent given a fixed expert skill scores 86.67, compared with 89.47 for unrestricted evolution and 71.58 for reset state. Much of the improvement is therefore available from a good procedure written in advance. Continued updating may still help, but this comparison leaves its added value over strong static expertise unresolved. [FinEvo-Bench, Table 5](https://arxiv.org/html/2608.06144v1).

Another alternative is to spend the effort on more attempts at the task. *Rethinking the Evaluation of Harness Evolution for Agents* finds that generating solutions in parallel beats the tested harness-evolution method when each receives five attempts. In a separate test on 34 tasks excluded from harness development, the evolved harness scores 68.3 against 67.7 for the original. That small difference challenges the assumption that a score rising during development means the harness will help elsewhere. Still, equal numbers of attempts do not mean equal total costs. A useful harness might repay its development cost over thousands of future tasks, so the comparison needs to include how often it will be reused. [Rethinking the Evaluation of Harness Evolution for Agents, Tables 1–3 and §4.4](https://arxiv.org/abs/2607.12227v2).

Learning can also undo earlier gains. AgentStream tests six benchmarks with 50 tasks each, using three models, five methods, and three task orders. When tasks from different benchmarks are mixed together, the average gain is just 0.90 percentage points, with some combinations improving and others getting worse. R-Zero shows a different form of deterioration: its two-model system's math score falls from 49.12 at training step 45 to 46.52 at step 60. These studies use different methods and scores, so their results cannot be combined into a single estimate. Both show why we need to follow performance over time. The best moment in a run does not tell us what further learning will do, and these results alone cannot establish whether bad feedback, changing training problems, or interference with earlier learning caused the declines. [AgentStream, Tables 2 and 11–13](https://arxiv.org/html/2608.00155v1); [R-Zero, Appendix D, Table 6, and Appendix E](https://arxiv.org/abs/2508.05004v4).

The evidence for learning better ways to improve is promising, but still limited. Hyperagents tests whether agents can continue improving after moving to a new domain. On mathematical grading, the transferred system scores 0.640 versus 0.610 for the comparison system, but the difference is not statistically significant across five runs. Dream-RSI reports better discovery results than a controller whose exploration policy stays fixed. Yet its guarantee of avoiding worse scores applies only to replaying recorded searches. It cannot guarantee improvement on paths the system has never explored. Likewise, showing that a discovered solver works on new data does not establish that the controller can learn to search effectively in a new field. [Hyperagents, §5.3 and Figure 4](https://arxiv.org/abs/2603.19461v1); [Dream-RSI, §§3–4](https://arxiv.org/html/2609.14858v1).

## What would make the case stronger?

The strongest competing explanation is that many apparent gains come from specializing in familiar tasks and spending more computation. The fixed-skill and extra-attempt comparisons give that explanation weight. At the same time, the gains from keeping experience and learning to write better update data are reasons to take these methods seriously. The current evidence cannot tell us how much each explanation accounts for across the field. It does tell us which comparisons matter.

We propose an experiment with four versions of the same starting agent. One uses a strong fixed procedure. A second starts fresh but gets extra attempts. A third keeps experience and uses a fixed method for making improvements. The fourth can also revise that improvement method. All four receive the same task stream, access to feedback, and total resource budget. This would help separate the value of prior expertise, extra computation, accumulated experience, and a changing learning method.

After development, the agents would face new kinds of tasks and a later period of work. Evaluation would track earlier abilities as well as new successes, record failures, and count the full cost of search, training, task execution, and judging. Repeated independent runs and a separately designed evaluator would reduce the chance of mistaking a lucky run or adaptation to one grading rubric for a reusable improvement. If the fourth agent reliably beat the third, that would strengthen the case that learning to improve has value. A claim of sustained acceleration would require more: successive cycles would need to produce improvements increasingly efficiently. This is a proposed test, not a finding of the reviewed studies.

The practical questions follow from how each system learns. An agent with a growing library must find useful lessons and discard misleading ones. A model that updates its weights must absorb new information without losing old abilities. A system that rewrites its improvement code must show that the new method works beyond the problems that shaped it. Research reviewed through September 16, 2026 shows useful progress on these questions. It has yet to establish an agent that keeps becoming better at improving itself across domains, with lasting gains that justify the full cost.
