# Self-evolving agents: what experience makes possible

## A failed change can still teach something

An agent tries to improve its instructions, tests the new version, and gets a worse result. Should it throw the whole attempt away? WikiSkill makes a useful distinction: the proposed skill can be rolled back while the knowledge gathered during the attempt survives. Its working procedure returns to an earlier version, but its next proposal need not start from the same ignorance. This is a concrete promise of self-evolving agents: work done today can make tomorrow's work better, even when today's experiment fails. [WikiSkill, §3 and Figure 2](https://arxiv.org/abs/2608.27454v1).

The promise contains a difficult judgment. An unsuccessful edit may reveal a useful constraint, or it may leave behind a convincing but mistaken explanation. Keeping more experience therefore does not automatically mean learning more. The system has to turn what happened into guidance, decide when that guidance applies, and discover whether using it actually helps.

The central question is what experience makes possible in later work. Learning a recurring procedure can be valuable without transferring to a different profession. Learning a method that produces better procedures in a new setting is a further achievement. Sustained compounding requires more again: successive improvements must make further learning more efficient. The evidence supports useful forms of the first achievement and promising, bounded examples of the second. It has not established the third. Understanding the distance between them begins with following an experience through the system.

## How an experience becomes a working procedure

WikiSkill starts with records of the agent's actions, tool outputs, and answers. A separate agent examines those records and consolidates patterns in a persistent wiki. Another uses the wiki and the original traces to propose a skill: instructions, scripts, or resources the task-solving agent can use. The candidate is evaluated on validation tasks before it replaces the active skill. The task-solving agent receives the skills directly; the wiki is available to the agents maintaining and proposing them. Each component has a different job: preserve what happened, interpret it, or tell the agent what to do next. [WikiSkill, §§2–3](https://arxiv.org/abs/2608.27454v1).

That separation explains why rejecting an edit need not erase the experience. A failed proposal and its result can help the next proposal avoid the same mistake. It also exposes a weakness that “learn from experience” can conceal: the validation gate checks the proposed procedure, while the retained interpretation can continue influencing later proposals. My reading is that memory needs its own standards of revision and relevance; approving a skill and trusting every lesson behind it are different decisions. [WikiSkill, §3](https://arxiv.org/abs/2608.27454v1).

The resulting skills do help in the paper's tests. For Qwen-3.5-9B, average accuracy across five equally weighted benchmarks rises from 29.9% without skills to 47.4% with WikiSkill. The study uses three evolution runs and separate development and test data. But it supplies skills directly, avoiding the problem of finding the right one, and its validation sets are small. A smaller model also gets worse on OfficeQA. The result supports useful learned procedures under this protocol; it leaves open how reliably an agent can select and maintain them in everyday use. [WikiSkill, Table 1 and Appendix B](https://arxiv.org/abs/2608.27454v1).

The broader idea predates this particular architecture. ExpeL extracts insights from trial-and-error experience and retrieves examples for unseen tasks while leaving the language model fixed. The important change is in the information available to the model when it acts. An agent can consequently learn something reusable even when none of the numerical parameters inside its model change. [ExpeL, §§3–4](https://arxiv.org/abs/2308.10144v3).

There are reasons to put the lesson elsewhere. If a failure concerns how tools are called or how work is organized, the system can revise the prompts and software surrounding the model—its *harness*. GEPA uses execution records to propose and evaluate prompt revisions. Automated Design of Agentic Systems lets a fixed designing agent write candidate agent programs. In these cases the accumulated lesson becomes part of the procedure followed on future tasks. Changing that procedure enlarges what can be learned, but a better resulting program does not yet show that the procedure for inventing programs has improved. [GEPA, Algorithm 1](https://arxiv.org/abs/2507.19457v2); [ADAS, §§3–4](https://arxiv.org/abs/2408.08435v2).

SEAL asks whether a model can instead learn to prepare material that changes its own weights, the parameters adjusted during training. Given a passage, the model generates training content; an update is applied; performance after that update determines which generated material was useful. The outer training process thus rewards writing something the model can learn from. In the single-passage experiment, this learned generator yields 47.0% accuracy, compared with 39.7% for synthetic data produced without learning that policy, over 974 questions from 200 held-out passages. Later sequential updates can nevertheless damage earlier knowledge. The lesson has moved into the model, but the obligation to check its future consequences remains. [SEAL, §3, Table 2, Figure 6 and Appendix B](https://arxiv.org/abs/2506.10943v2).

These examples explain what persists: useful information, a working procedure, or a changed model. They also show why the location of a change cannot settle its value. To find out whether the agent has gained something, we need to ask what it can do with that change on work that did not produce it.

## What does learning add to a good starting agent?

A direct test lets one agent retain experience and makes another start fresh. FinEvo-Bench does this across 120 financial tasks, four agent frameworks sharing one model, and three shuffled task orders. Keeping experience raises scores by 9.33–19.37 points on the benchmark's grading rubrics. The tasks reuse professional procedures across distinct cases, making this a useful setting for accumulated expertise. The main effects lack across-run uncertainty intervals. [FinEvo-Bench, §§4.1–4.3 and Table 3](https://arxiv.org/html/2608.06144v1).

But what if the agent already starts with a good procedure? In a separate comparison using one framework, a fixed expert skill scores 86.67, unrestricted evolution 89.47, and reset state 71.58. Much of the benefit is available through expertise supplied beforehand. This does not make the learned procedure worthless; it changes the practical question to what continued updating adds beyond a strong starting point. The comparison does not establish that the remaining advantage repays the work of learning. [FinEvo-Bench, Table 5](https://arxiv.org/html/2608.06144v1).

Nor does the difficulty of writing a good skill in one attempt establish that iterative learning cannot work. SkillsBench finds that curated skills help on average, while self-generated skills perform worse than no skills in three dedicated configurations. Its generation condition is a single attempt, without the repeated outcome feedback used by an evolution loop. This is a reason to compare against strong expert guidance and to distinguish one-shot authoring from learning through tests. It cannot settle the value of the latter. [SkillsBench v4, Tables 2 and 6, Appendix D.6](https://arxiv.org/abs/2602.12670v4).

A second alternative spends the available effort on more attempts at the current task. *Rethinking the Evaluation of Harness Evolution for Agents* finds that parallel solution sampling beats the tested evolution method when both receive five attempts. In a separate experiment on 34 tasks excluded from harness development, the evolved harness scores 68.3 against 67.7 for the original. A rising development score can therefore coexist with little advantage on new work. [Rethinking the Evaluation of Harness Evolution for Agents, Tables 1–3](https://arxiv.org/abs/2607.12227v2).

The comparison becomes more interesting when the harness is reused. Equal attempt counts do not imply equal total costs, and developing a procedure once may pay off across many later tasks. Extra attempts can also supply the experience from which a procedure is learned; ReasoningBank explicitly combines test-time search with retained lessons. Learning and search can reinforce each other. The useful test measures their contributions and counts both development and later execution costs over a stated amount of reuse. [Harness evaluation, §4.4](https://arxiv.org/abs/2607.12227v2); [ReasoningBank, §§3–4](https://arxiv.org/abs/2509.25140v2).

This gives a practical interpretation of self-evolution: it is an investment in future work. Whether that investment succeeds depends on how often the lesson remains applicable, what it costs to use, and whether later learning preserves it.

## The next task can change the verdict

A lesson that worked yesterday may be irrelevant today, and another update may make the agent worse at something it previously knew. AgentStream tests this problem using six benchmarks with 50 tasks each, three models, five methods, and three task orders. In mixed task streams, the average gain is 0.90 percentage points, with both improvements and regressions across configurations. This cannot be compared numerically with FinEvo's rubric-score gains: the tasks, feedback, and measurements differ. It does show why a favorable result on recurring procedures cannot stand in for a test across diverse work. [AgentStream, Tables 2 and 11–13](https://arxiv.org/html/2608.00155v1).

Keeping a library is therefore an ongoing decision about what to use and revise. Library Drift examines retrieval, storage limits, and skill retirement; removing skills too aggressively can itself hurt performance. An obsolete lesson and a prematurely deleted useful lesson create opposite problems. Meanwhile, EvoHarnessBench changes available tools, skills, or specialist agents along with tasks. Even accurate old knowledge can become unreliable when the interface through which the agent acts changes. Together, these studies motivate testing both the retained procedures and the conditions under which the agent selects them. [Library Drift, §§5–7](https://arxiv.org/abs/2605.19576v3); [EvoHarnessBench, §§3–4](https://arxiv.org/abs/2609.04280v2).

The feedback used to learn matters just as much. Absolute Zero generates code-reasoning exercises and checks them by execution. R-Zero pairs a problem-generating model with a solver and uses model-generated answers in its training process. Execution supplies an external check within the designed environment; agreement among generated answers can reproduce a shared mistake. Generating exercises autonomously does not remove the need for a trustworthy standard of correctness. [Absolute Zero, §3](https://arxiv.org/abs/2505.03335v3); [R-Zero, §2](https://arxiv.org/abs/2508.05004v4).

In R-Zero's two-model experiment, the math score falls from 49.12 at training step 45 to 46.52 at step 60. More training has reversed part of the earlier gain. The result does not isolate the cause: label quality, problem difficulty, and the distribution of generated training data also change. It establishes a narrower but important point: reporting the best moment in a run does not establish that the process can keep improving. [R-Zero, Appendix D, Table 6, and Appendix E](https://arxiv.org/abs/2508.05004v4).

Deterioration is not inevitable. *Rethinking Continual Experience Internalization* finds that a default recipe for repeatedly training on experience deteriorates, then tests a revised recipe using general lessons, relevant guidance at each decision, and successful experience-guided training trajectories. It obtains bounded gains across three iterations, though one benchmark's trajectory remains uneven. This positive counterexample shifts the question from whether repeated learning must fail to which update choices preserve its benefits. The two-model, three-iteration study does not establish indefinite durability. [Rethinking Continual Experience Internalization, §§3–5, Figure 1 and Table 4](https://arxiv.org/html/2606.04703v1).

Production systems make the feedback dependency especially visible. Shopify's account of Sidekick describes taking failed conversations, having stronger models propose repairs, replaying the conversations, and using successful repairs for training. Unresolved cases go to human annotators. The system also revises its harness and trains on accumulated old and new trajectories. Experience becomes useful through a substantial process of diagnosis, correction, selection, and retention. [Shopify Engineering, “Sidekick's continual learning loop,” August 2026](https://shopify.engineering/sidekicks-continual-learning-loop).

That account gives a concrete engineering design, but no controlled comparison separating the stages or cycle-by-cycle evidence of continued improvement. Its judges help both select updates and assess quality, so a blind spot could persist through the loop. The broader measurement problem is observable in engineered tool environments: the Reward Hacking Benchmark scores evaluator integrity separately from task correctness. These results motivate an evaluator outside the agent's edit permissions. A system that can improve its working procedure must still be measured against a standard its edits cannot quietly weaken. [Shopify, evaluation and training sections](https://shopify.engineering/sidekicks-continual-learning-loop); [Reward Hacking Benchmark, §§4–6](https://arxiv.org/abs/2605.02964v1).

So far, the successful systems have learned within processes whose crucial decisions are at least partly supplied by designers. The next question is whether experience can improve those decisions too.

## Can the agent learn a better way to learn?

WikiSkill illustrates the boundary. Its knowledge and skills evolve, but designers specify how records are examined, proposals are generated, and edits are accepted. A better skill is evidence about what that process produces. To show that the process has learned, we need to let some of those decisions change and test whether the changed method makes useful future improvements.

That possibility exists at several scales. MemSkill maintains operations for constructing memories and allows a designer component to revise them, extending learning from memory contents to the operations that preserve future experience. STOP lets a system edit improvement code; Hyperagents places task-solving and improvement code in the same editable implementation. These mechanisms make the learning procedure a candidate for change, while still relying on externally specified models, evaluations, or selection rules. Edit permission makes the hypothesis testable; it does not demonstrate the benefit by itself. [MemSkill, §§3–4](https://arxiv.org/abs/2602.02474v2); [STOP, Algorithm 1](https://arxiv.org/abs/2310.02304v3); [Hyperagents, §3](https://arxiv.org/abs/2603.19461v1).

Hyperagents supplies a particularly useful test. Agents developed on paper review and robotics reward design are transferred to mathematical grading. Their improvement code is then held fixed while generating candidate task agents for 50 iterations. Across five runs, the transferred implementations achieve a median improvement in held-out score of 0.630, with a reported 95% bootstrap interval of 0.540–0.630; the initial implementation's median is zero. This is positive evidence that useful improvement behavior can travel to a new domain. The whole implementation transfers, however, and the initial task agent has formatting failures. The experiment does not isolate the contribution of improvement code from the rest of the transferred implementation. [Hyperagents, §5.2, Figure 3 and Appendix D](https://arxiv.org/abs/2603.19461v1).

A second experiment asks whether the transferred starting point still helps when the improvement method can continue evolving. After 200 iterations, transferred agents score 0.640 versus 0.610 for agents starting from the initial implementation; the difference is not statistically significant across five runs. The first experiment supports transferable improvement behavior under a fixed generation procedure. The second leaves its added long-run advantage uncertain. Neither shows successive cycles becoming more efficient at producing further gains. [Hyperagents, §5.3 and Figure 4](https://arxiv.org/abs/2603.19461v1).

Dream-RSI offers another way to make the improvement process learn: it uses recorded searches to revise the controller deciding what to explore. Replaying those histories can make testing a controller change cheaper than rerunning every experiment. Yet the guarantee of avoiding worse scores applies to recorded searches, not unexplored paths, and its three mathematics comparisons include an improvement, a regression, and a tie. The method explains how a search policy can benefit from experience while leaving its ability to learn in unfamiliar settings unsettled. [Dream-RSI, §§3–4, Figure 3 and Table 1](https://arxiv.org/html/2609.14858v1).

This is the gap between useful meta-learning and sustained compounding. A better starting implementation, a better search controller, and a higher final score can each be valuable. Sustained compounding asks whether improvements repeatedly increase the efficiency of producing the next improvement, after accounting for difficulty and resources. The theoretical *Economics of Recursive Self-Improvement* makes the importance of that condition explicit, while allowing other research inputs to become bottlenecks. Its uncertain research-productivity assumptions are not measurements of an agent loop becoming self-sustaining. [The Economics of Recursive Self-Improvement, §§2–4](https://arxiv.org/abs/2609.15802v1).

## What would distinguish the achievements?

A useful experiment would begin with the alternatives already exposed by the evidence. Compare a strong fixed procedure, an agent that starts fresh and spends its resources on extra attempts, an agent retaining experience under a fixed improvement method, and an agent allowed to revise that method. Give them the same task stream and feedback access under a common total resource ceiling. The fixed and editable improvers should begin with identical task code, improvement code, and retained state. A paired reset control would separately test the contribution of retained experience; the four alternatives alone do not isolate four independent causes.

Then ask two different questions. Freeze each developed system and test fresh cases, new task families, and earlier abilities: what has the accumulated experience already made possible? Separately, allow copies to learn on new streams: what can they learn next? To isolate a learned improvement method, attach the original and learned methods to identical task agents with identical memory, hold both methods fixed, and compare the gains they produce. This would address a question left open when an entire evolved implementation transfers.

Repeated runs, an independent evaluator, and accounting for search, training, execution, and judging would make those comparisons informative. Report development cost alongside operating cost at explicit amounts of reuse. A reliable advantage for the editable improver would establish practical value under those conditions. Evidence of sustained compounding would require multiple cycles of improved learning efficiency under a consistent measure of difficulty and resources. These are proposed tests, not results the existing studies already provide.

The failed WikiSkill edit is a small example of the larger opportunity. An attempt can be worth keeping because it changes what the system can do next. The same standard should apply as the changes become more ambitious: a useful procedure should help on later work; a learned improvement method should produce better future procedures; a claim of compounding should show further learning becoming more efficient. Keeping those achievements distinct lets us recognize useful learning today and specify what the next advance would have to demonstrate.
