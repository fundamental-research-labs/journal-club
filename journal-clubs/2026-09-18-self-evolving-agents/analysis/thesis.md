# Self-evolving agents: when experience helps with the next task

## Learning that lasts

An agent that solves a difficult task leaves behind more than an answer. Its failed attempts, useful shortcuts, and working code might help with the next problem—if it can turn them into something worth keeping. Early systems explored two ways to do this. Reflexion stores written feedback to guide later attempts at a task; Voyager builds a library of executable skills as it explores Minecraft. Both make experience available for later use, but they pose different tests of learning. Fixing a mistake on a retry does not, by itself, show that an agent has become better at new work. [Reflexion, §§3–4](https://arxiv.org/abs/2303.11366v4); [Voyager, §§2–3](https://arxiv.org/abs/2305.16291).

A useful way to understand *self-evolution* is to ask what experience changes and whether that change lasts. An agent might retain a memory, revise its instructions, save a program, or update the model's weights—the numerical parameters changed during training. “Self” describes the agent's role in making those changes; people may still supply its feedback, set its goals, and write the rule that decides which changes survive. The important boundary is between what the agent can change and what remains outside its control. [SEAL, §3](https://arxiv.org/abs/2506.10943v2); [STOP, §3 and Algorithm 1](https://arxiv.org/abs/2310.02304v3).

Self-evolving agents can turn experience into reusable improvements. Their scope and value depend on how the system selects changes, preserves useful knowledge, and applies it to later work. Learning a recurring procedure can be valuable even if it never transfers to a different profession. Transferring a learned method for making improvements is a further achievement, for which there is promising evidence. Sustained, economical compounding—where better learning methods repeatedly make further improvement more efficient—remains unestablished. These claims require different tests: whether experience helps, how far its benefit travels, and whether the benefit justifies the full cost.

## What an agent can change

One way to learn is to keep better records. The underlying model stays the same, but it can consult lessons or reuse programs from earlier tasks. WikiSkill takes this idea a step further by separating accumulated knowledge from the skills selected for use. If a proposed skill edit fails, the system can reject the edit while keeping what it learned from the attempt. This separates two decisions: what might be worth remembering and what is ready to guide action. A failed edit can inform a later proposal without immediately changing the deployed skill. The distinction also creates an obligation to check the retained knowledge: rejecting a bad procedure does not guarantee that every lesson drawn from it is sound. In its experiments, Qwen-3.5-9B's average accuracy across five benchmarks rises from 29.9% to 47.4%. Each benchmark receives equal weight in that average, and the study reports three evolution runs using separate development and test data. The gain is encouraging, but the setup makes some parts of the problem easier: the agent receives skills directly, rather than having to find the right ones, and the validation sets used to select changes are small. A smaller model also gets worse on OfficeQA. [WikiSkill, §§3–4, Table 1 and Appendix B](https://arxiv.org/abs/2608.27454v1).

Cross-task use of experience was already explicit in ExpeL in 2023: a frozen agent extracts insights from trial-and-error training and retrieves successful examples for unseen tasks. ReasoningBank later combines lessons from self-judged successes and failures with additional test-time attempts. The latter makes an important possibility visible: extra computation and memory can reinforce each other, because more attempts supply better comparisons from which to learn. The useful question is how much each contributes, rather than assuming they are competing explanations in every system. [ExpeL, §4](https://arxiv.org/abs/2308.10144v3); [ReasoningBank, §§3–4](https://arxiv.org/abs/2509.25140v2).

Keeping experience is only the first step. An agent must decide what to write, which records to retrieve, and when a lesson has stopped being useful. Agentic Context Engineering separates generating an answer, reflecting on its outcome, and curating a structured playbook, so that a small update need not rewrite everything. MemRL instead attaches learned utility values to memories and uses rewards to influence retrieval. These methods put learning in different places: one revises the guidance, while the other changes which experience the agent trusts. Their benefits depend on the quality of the stored lessons and their relevance to the next task. [ACE, §3](https://arxiv.org/abs/2510.04618v3); [MemRL, §§4–6](https://arxiv.org/abs/2601.03192v2).

The rule for making memories can itself become a learned object. SelfMem lets an agent organize a workspace and later refines its memory-strategy instructions; its evaluation primarily measures answers about long conversations. MemSkill separates a memory bank from a bank of reusable memory operations, combining learned skill selection with a designer that revises those operations. This extends the question beyond whether a memory contains the right fact: can the system learn a better way to preserve future experience? It also makes the boundary of autonomy more precise. A changing memory procedure can still depend on fixed language models, rewards, and selection rules. [SelfMem, §§3–5](https://arxiv.org/abs/2607.03726v1); [MemSkill, §§3–4](https://arxiv.org/abs/2602.02474v2).

Useful skills need a reliable path from an individual success or failure to a reusable procedure. EvoSkill separates execution, failure analysis, and skill construction, but its transfer result uses one evaluation run on 128 browsing questions. [EvoSkill, §§2–3](https://arxiv.org/abs/2603.02766v1). Trace2Skill consolidates local trajectory lessons into edits and tests their transfer, including an AIME configuration that gets worse. [Trace2Skill, §§2–3](https://arxiv.org/abs/2603.25158v5). SkillOpt regulates changes through bounded patches and validation gates, with disjoint test data but no independent-run intervals in the main results. [SkillOpt, §§3–4](https://arxiv.org/abs/2605.23904v2). These approaches expose choices that “learn from experience” leaves unspecified: how much to generalize, whether to merge lessons, and how much testing an edit deserves. Positive transfer results coexist with regressions, small selection sets, and unresolved differences in optimization budgets.

An agent can also change the instructions and software that organize its work, often called its *harness*. GEPA examines records of an agent's actions and results, proposes revised prompts, and keeps candidates that work well on different examples. Here, the lesson becomes part of the instructions for future work. SEAL takes a different route: it trains a model to write the data and instructions used to update its own weights. In an experiment where the model learns from one passage at a time, SEAL reaches 47.0% accuracy, compared with 39.7% when the model generates training data without first learning how to do so. The evaluation covers 974 questions from 200 passages held out of training. This shows that a model can learn to produce more useful training material in that setting. It does not tell us whether changing weights is generally better than changing prompts; the studies use different tasks and budgets. [GEPA, Algorithm 1 and §4](https://arxiv.org/abs/2507.19457v2); [SEAL, Table 2 and Appendix B](https://arxiv.org/abs/2506.10943v2).

Changing software opens a larger search space than editing instructions alone. Automated Design of Agentic Systems uses a fixed meta-agent to program candidate agents, evaluate them, and build an archive of designs. AFlow searches code-defined workflows with execution feedback and a tree that records earlier modifications. Their selected designs can be reused after search, and their held-out tests provide evidence beyond development performance. The optimizing procedure nevertheless remains fixed: a better agent design need not imply a better designer. [ADAS, §§3–4](https://arxiv.org/abs/2408.08435v2); [AFlow, §§4–5](https://arxiv.org/abs/2410.10762v4).

A further question is which candidate deserves more development. The Darwin Gödel Machine keeps an archive of coding agents and branches from it, allowing a less successful intermediate agent to become a useful ancestor. The Huxley–Gödel Machine makes that possibility explicit in its selection rule: it estimates a candidate's value through the performance of its descendants. These are distinct proposals about how to search, not evidence that every additional generation improves. Both include transfer checks, but their main search comparisons have limited repeated-run evidence, and selecting promising descendants remains an externally defined procedure. [Darwin Gödel Machine, §§3–6](https://arxiv.org/abs/2505.22954v3); [Huxley–Gödel Machine, §§3–4](https://arxiv.org/abs/2510.21614v3).

What the software does matters as much as its search history. Agentic Harness Engineering edits executable memory, tools, and middleware as well as prompts. Its evolved system uses fewer tokens on a separate software benchmark when timeouts are excluded from the mean; the success gain there is only 0.4 percentage points. [Agentic Harness Engineering, Tables 2–3](https://arxiv.org/abs/2604.25850v4). Evo-Harness compiles execution context into skills and guidance for later tasks; its feedback ablation shows that self-generated feedback can make the original agent worse. [Evo-Harness, §§4.5–4.6 and Table 4](https://arxiv.org/abs/2608.15071v2). In embodied settings, SHAPER evolves both procedural instructions and the code that gathers context. Its tests include unseen target categories and task forms, although one selected pair of artifacts and category-level regressions limit the generality of the result. [SHAPER, §§3–4](https://arxiv.org/abs/2608.11350v2). These studies make reuse more concrete than a rising development score alone.

## Where the learning signal comes from

A system can generate its own exercises without generating its own standard of correctness. Absolute Zero proposes code-reasoning problems and checks them by execution. That creates a useful source of training signal, but “zero data” describes the absence of curated downstream examples during self-play, not the absence of pretraining, designed environments, or rewards. Test-Time Reinforcement Learning takes a different approach: it uses majority answers as provisional labels while adapting to an unlabeled test batch. Its gains show that training can exploit that batch; they do not, by themselves, establish transfer to future unseen inputs. Executable feedback and model consensus therefore make different demands on verification. [Absolute Zero, §3 and Appendix D](https://arxiv.org/abs/2505.03335v3); [TTRL, §§2–3](https://arxiv.org/abs/2504.16084v3).

The environment can also change in response to the agent. Agent-World builds executable environments, diagnoses weaknesses, and generates targeted training tasks. Its external benchmark results widen the positive evidence beyond one coding problem, but private training inputs, incomplete resource accounting, and inconsistent values in one evolution table limit attribution. A web-exploration study instead trains a policy to build a website guidebook before receiving the eventual question. Its guidebooks can help another model, but their construction can take substantial exploration, and the policy does not update its weights during deployment. A better environment curriculum, a better guidebook, and a better learning algorithm are related achievements with different persistence and transfer tests. [Agent-World, §§3–4](https://arxiv.org/abs/2604.18292v1); [World Knowledge Exploration, §§3–4](https://arxiv.org/abs/2604.18131v1).

A more ambitious goal is to improve how the system learns. R-Zero pairs a model that invents problems with a model that learns to solve them, allowing the training problems to change as learning proceeds. STOP and Hyperagents let the system edit the code that proposes improvements. Dream-RSI uses records of earlier searches to revise a controller that decides what to explore next. These methods raise a further question: can an agent learn a better way to improve, then carry that method into a new setting? Finding a better solution to one problem is only part of the evidence needed. This ambition also predates the latest papers: STOP was already editing improvement code in 2023. [R-Zero, §2](https://arxiv.org/abs/2508.05004v4); [STOP, Algorithm 1](https://arxiv.org/abs/2310.02304v3); [Hyperagents, §3](https://arxiv.org/abs/2603.19461v1); [Dream-RSI, §3](https://arxiv.org/html/2609.14858v1).

There is also a bridge between memory and training: a model can learn to act without the experience notes that helped teach it. *Rethinking Continual Experience Internalization* studies repeated cycles of this process in web reasoning. Its default training on student-generated trajectories deteriorates across iterations. A revised recipe uses general principles, selects relevant experience at each decision, and trains on successful trajectories generated with that experience. The resulting bounded gains challenge an overly pessimistic reading of collapse: failure is not inevitable, and the update recipe matters. The study covers two model sizes and three iterations without repeated-training uncertainty; it does not establish continuing improvement across arbitrary domains. [Rethinking Continual Experience Internalization, §§3–5, Figures 1 and 6](https://arxiv.org/html/2606.04703v1).

Several newer systems combine update types. SIA lets a fixed feedback model request either a harness edit or a weight update; its reported schedule moves to training after harness search stalls. MetaRSI studies policies for composing data, harness, and weight changes. ScienceBuddy alternates harness refinement and model training for scientific assistance. These are useful tests of interaction between components, but they differ in what the improver can change. SIA repeatedly uses its nominal test evaluator during optimization; MetaRSI's stated budget matching lacks an independently inspected realized-cost ledger; ScienceBuddy's released recipe differs from the reported experiment. The positive endpoints warrant further study without treating all three as demonstrations of a learning rule that keeps improving itself. [SIA, §§5–6](https://arxiv.org/abs/2605.27276v2); [MetaRSI, §§3–5 and Appendix F](https://arxiv.org/abs/2609.06396v2); [ScienceBuddy, §§4 and 7](https://arxiv.org/abs/2609.17523v1).

In practice, a system can combine several of these methods. Shopify's August 2026 account of Sidekick describes a process that revises the harness, repairs unsuccessful sequences of actions, trains model weights, and compresses prompts. It shows how a production system can turn failures into changes at several levels. The article does not, however, report experiments that separate each step's contribution or track quality over successive learning cycles. It gives us a concrete design to study, while leaving the benefit of continual learning itself difficult to measure. [Shopify Engineering, “Sidekick's continual learning loop”](https://shopify.engineering/sidekicks-continual-learning-loop).

The supporting infrastructure deserves attention in its own right. Reef connects serving records, delayed feedback, learning recipes, evaluation, and versioned updates. Its released harness comparison includes a fresh evaluation on the same tasks used for search, which tests repeatability on those tasks rather than transfer to new ones. NVIDIA's NemoClaw account describes a structured memory system with provenance and user corrections, but the evaluated self-model adapter and generated memory are not released. These original engineering accounts reveal practical work that benchmark methods often leave implicit: attributing feedback to the correct version, reconciling changed facts, and deciding what can be reproduced from a release. They do not provide an independent estimate of the general benefit of continual learning. [Reef, pinned README and Meta-Harness report](https://github.com/Human-Agent-Society/reef/tree/401db3670d34b1b5a77989234272e0bee4b90ce8); [NVIDIA, memory-driven agent and linked evaluation](https://developer.nvidia.com/blog/building-a-memory-driven-agent-with-nvidia-nemoclaw/).

## When does retained experience earn its cost?

A useful first test is to let one agent keep its experience and make another start fresh each time. FinEvo-Bench does this with four agent software frameworks, all using the same underlying model. Each processes 120 financial tasks in three shuffled orders. Keeping experience raises average scores by 9.33–19.37 points on the benchmark's grading rubrics compared with resetting the agent. These are gains on recurring professional procedures, where lessons from one case can help with another. The paper does not provide uncertainty intervals across runs for these main effects. [FinEvo-Bench, §§4.1–4.3 and Table 3](https://arxiv.org/html/2608.06144v1).

Learning those recurring procedures is a useful outcome. Its practical advantage depends on what the agent would otherwise have been given: starting fresh without useful guidance may be an undemanding comparison. In a separate FinEvo test using one framework, an agent given a fixed expert skill scores 86.67, compared with 89.47 for unrestricted evolution and 71.58 for reset state. Much of the improvement is therefore available from a good procedure written in advance. Continued updating may still help, but this comparison leaves its added value over strong static expertise unresolved. [FinEvo-Bench, Table 5](https://arxiv.org/html/2608.06144v1).

The baseline must also reflect what an agent can already do with expert instructions. SkillsBench v4 tests 87 tasks across 18 model–harness configurations: curated skill packages raise average pass rate from 33.9% to 50.5%. Self-generated skills do worse than no skills in three dedicated configurations. But task construction filters out low-signal submissions, curated packages include human work and executable resources, and 13 tasks get worse with curated skills. Its one-shot generation condition is not a test of an iterative learning system supplied with outcome feedback. The observed deficit therefore does not establish the impossibility of learning skills. Conversely, beating an unassisted agent would leave the curated-skill comparison unresolved. [SkillsBench, Tables 2 and 6, Appendix D.6](https://arxiv.org/abs/2602.12670v4).

Another alternative is to spend the effort on more attempts at the task. *Rethinking the Evaluation of Harness Evolution for Agents* finds that generating solutions in parallel beats the tested harness-evolution method when each receives five attempts. In a separate test on 34 tasks excluded from harness development, the evolved harness scores 68.3 against 67.7 for the original. That small difference challenges the assumption that a score rising during development means the harness will help elsewhere. Still, equal numbers of attempts do not mean equal total costs. A useful harness might repay its development cost over thousands of future tasks, so the comparison needs to include how often it will be reused. [Rethinking the Evaluation of Harness Evolution for Agents, Tables 1–3 and §4.4](https://arxiv.org/abs/2607.12227v2).

Transfer can fail even when a developer has reserved a test set. HarnessDev follows successive harness versions and compares their changes on development feedback with changes on a separate held-out set. The directions agree on 34 of 64 adjacent version switches. This is a warning about selecting improvements, not a claim that only 34 versions are useful. SEA-Eval asks a complementary question through task sequences: can the agent reuse experience on a similar task and after unrelated intervening work? EvoHarnessBench changes the available tools, skills, or specialist agents as well as the tasks. Together these designs distinguish changes in task content, task order, and the interface through which an agent acts—three ways that yesterday's useful procedure may become unreliable. [HarnessDev, evolution and version-switch analysis](https://arxiv.org/abs/2609.01437v1); [SEA-Eval, §§4–5](https://arxiv.org/abs/2604.08988v3); [EvoHarnessBench, §§3–4](https://arxiv.org/abs/2609.04280v2).

Learning can also undo earlier gains. AgentStream tests six benchmarks with 50 tasks each, using three models, five methods, and three task orders. When tasks from different benchmarks are mixed together, the average gain is just 0.90 percentage points, with some combinations improving and others getting worse. R-Zero shows a different form of deterioration: its two-model system's math score falls from 49.12 at training step 45 to 46.52 at step 60. These studies use different methods and scores, so their results cannot be combined into a single estimate. Both show why we need to follow performance over time. The best moment in a run does not tell us what further learning will do, and these results alone cannot establish whether bad feedback, changing training problems, or interference with earlier learning caused the declines. [AgentStream, Tables 2 and 11–13](https://arxiv.org/html/2608.00155v1); [R-Zero, Appendix D, Table 6, and Appendix E](https://arxiv.org/abs/2508.05004v4).

For a skill library, avoiding deterioration requires more than retaining successful text. Library Drift studies routing, storage limits, and retirement; its ablations show that overly aggressive retirement can itself be harmful. *When Self-Evolution Backfires* examines how a bad admitted skill can influence descendants, making removal of the original insufficient. Its admission gate helps on a small untouched test set, while the main collapse trajectory is measured on tasks repeatedly used for skill creation. These results motivate provenance and validation, but neither establishes a universal rate of contamination or a guarantee that gating prevents future regressions. [Library Drift, §§5–7](https://arxiv.org/abs/2605.19576v3); [When Self-Evolution Backfires, method, Tables 1–4](https://arxiv.org/abs/2608.05810v1).

Reflection is also constrained by the explanations an optimizer knows how to consider. *Reflection in the Dark* constructs prompt-seed failures that reflective optimization struggles to escape; explicitly supplied failure hypotheses account for much of the recovery. This makes the designer's prior knowledge part of the explanation for apparent self-improvement. *Ground Truth First* poses a different challenge to memory systems: compare them with the complete history, test facts at the time they were true, and follow performance as histories lengthen. Its architecture comparisons are sensitive to horizon and judge, and its longitudinal population comprises six synthetic users. Better diagnosis and better evaluation can both change the apparent learning result. [Reflection in the Dark, Tables 1–3](https://arxiv.org/abs/2603.18388v2); [Ground Truth First, §§5–7](https://arxiv.org/abs/2607.21962v1).

A final risk is that the score itself becomes the object of improvement. RewardHackingAgents separately manipulates access to evaluators and held-out data in engineered ML workspaces. The Reward Hacking Benchmark uses broader tool workflows and scores integrity separately from task correctness. These studies do not measure how frequently all self-evolving agents cheat, but they show why success and evaluator integrity must be recorded separately. A system permitted to rewrite its workspace needs a trusted measurement boundary outside the changes it can make. Otherwise, a higher score can reflect a less informative test. [RewardHackingAgents, §§III–VI](https://arxiv.org/abs/2603.11337v1); [Reward Hacking Benchmark, §§4–6](https://arxiv.org/abs/2605.02964v1).

## Improving the search, or improving the ability to search?

A useful discovered program is a real achievement even when the search agent stays unchanged. AlphaEvolve searches for mathematical constructions and engineering algorithms using automatic evaluators. Karpathy's autoresearch makes a smaller experiment loop inspectable: edit training code, run a fixed-duration experiment, and accept or reject it using a validation metric. SoL-Pi releases reusable agent-efficiency extensions attributed to research loops. These examples make it possible to ask exactly where the improvement resides—in the produced algorithm, a trained model, or the agent's own future search procedure. Their value does not depend on counting all three as recursive self-improvement. [AlphaEvolve, §§2–3](https://arxiv.org/abs/2506.13131v1); [autoresearch, pinned experiment contract](https://github.com/karpathy/autoresearch/tree/228791fb499afffb54b46200aca536f79142f117); [SoL-Pi, pinned README](https://github.com/NVlabs/SoL-Pi/tree/2b791687a489a1d24da816cf1634d8ae1d36befd).

There is stronger evidence of changing search behavior when the optimizer itself is allowed to evolve. EvoX changes search strategies as well as candidate solutions. [EvoX, §§3–6](https://arxiv.org/abs/2602.23413v2). Escher-Loop maintains both solution programs and optimizer programs; on Circle Packing, its three-run static-pool ablation ties the full loop on area under the search curve and slightly exceeds its mean best score. [Escher-Loop, §§2–3 and Table 1](https://arxiv.org/abs/2604.23472v2). MLEvolve uses retrospective memory across search branches in machine-learning engineering, with a smaller ablation supporting a contribution from memory. [MLEvolve, §§3–4 and Table 3](https://arxiv.org/abs/2606.06473v1). These are consequential positive examples, but improvement during the search for one solution remains different from a reusable search policy that learns faster on a new problem. Iteration counts, task-evaluation budgets, and equivalent-token budgets also measure different resources.

Hyperagents provides a direct, bounded test of transferring an improvement method. In one experiment, agents developed on paper review and robotics reward design move to mathematical grading. Their improvement code is then held fixed while it generates candidate task agents for 50 iterations. Across five runs, transferred agents achieve a median improvement in held-out score of 0.630, with a reported 95% bootstrap interval of 0.540–0.630; the corresponding initial-agent median is zero. The authors report a significant difference. This is positive evidence that a learned agent implementation can carry useful improvement behavior into a new domain. It is not a clean isolation of improvement code alone: the whole implementation transfers, and the initial task agent fails to produce correctly formatted outputs. [Hyperagents, §5.2, Figure 3 and Appendix D](https://arxiv.org/abs/2603.19461v1).

A separate Hyperagents experiment asks whether that head start remains advantageous when the improvement method can continue changing. After 200 iterations, transferred agents score 0.640 versus 0.610 for agents starting from the initial implementation; the difference is not statistically significant across five runs. The two experiments establish different things. The first supports transfer of useful improvement behavior under a fixed generation procedure. The second leaves the added benefit of the transferred starting point uncertain after longer continued evolution. Neither establishes that successive cycles become increasingly efficient. [Hyperagents, §5.3 and Figure 4](https://arxiv.org/abs/2603.19461v1).

Dream-RSI approaches the problem by reusing search histories. Its controller can improve discovery quality and call counts relative to fixed exploration on several tasks, although its three mathematics comparisons include an improvement, a regression, and a tie. The mechanism is useful: recorded searches let the system test changes to exploration without repeating every online experiment. But its guarantee of avoiding worse scores applies only to replaying recorded searches, not to unexplored paths. Likewise, showing that a discovered solver works on new data does not establish that the controller can learn to search effectively in a new field. [Dream-RSI, §§3–4, Figure 3 and Table 1](https://arxiv.org/html/2609.14858v1).

The distinction matters for the more ambitious economic claim. *The Economics of Recursive Self-Improvement* models when better AI increases research productivity enough to sustain further acceleration. It distinguishes narrow gains in readily verified algorithmic work from broad capability and allows other inputs to become bottlenecks. Its calibration relies on uncertain assumptions and sparse evidence about AI's effect on research productivity; it is a conditional model, not a measurement of an agent loop becoming self-sustaining. The empirical question is therefore not simply whether one curve rises, but whether a more capable system produces further improvements more efficiently after accounting for the resources and constraints that enabled them. [The Economics of Recursive Self-Improvement, §§2–4](https://arxiv.org/abs/2609.15802v1).

## What would make the case stronger?

The evidence supports learning that is useful within a defined range of work, with some promising transfer of improvement methods. Specialization is one possible success: an agent that learns a recurring procedure has learned something, even if the lesson does not travel far. The stronger challenge is whether updating adds value beyond expertise supplied in advance or computation spent on fresh attempts. Those alternatives can also complement learning, since extra attempts provide experience to learn from. The comparison should measure their contributions without treating them as mutually exclusive explanations.

A useful experiment would compare four versions of the same starting agent. One would use a strong fixed procedure. A second would start fresh for each task and spend its available resources on extra attempts. A third would retain experience under a fixed improvement method. The fourth would also be allowed to revise that method. All four would receive the same task stream and access to feedback under a common total resource ceiling. These are practical alternatives, not an automatic decomposition of four causes. In particular, the third and fourth agents should begin with identical retained state, task-solving code, and improvement code; permission to revise the improvement method would be the experimental difference. A paired reset version of the third would separately test the contribution of retained experience.

Evaluation would then separate reuse from further adaptation. First, freeze each developed system's persistent state and measure performance on fresh cases, new task families, and earlier abilities. This tests what the accumulated changes already make possible. Separately, let copies resume learning on new streams. To test the learned improvement method itself, attach the original and learned methods to identical task agents with identical starting memory, hold each method fixed, and compare the gains they produce. That isolates a different question from transferring a whole evolved system, whose task code and stored expertise may already be better.

Repeated independent runs, an evaluator outside the agent's edit permissions, and accounting for search, training, execution, and judging would make the results more informative. Report both development cost and later operating cost at explicit amounts of reuse; an expensive update may be worthwhile over many tasks and wasteful over a few. A reliable advantage from revising the improvement method would support its practical value. Sustained acceleration would require repeated cycles to improve learning efficiency under a consistent measure of difficulty and resources. A higher final score alone cannot establish it.

The practical implication is to design for useful reuse. Memory needs relevant retrieval and a way to revise obsolete lessons. Weight updates need retention checks. Changes to improvement code need tests on problems that did not shape that code. These requirements follow from the different ways experience can help or interfere. The field has demonstrated useful steps along this path, including bounded transfer of improvement behavior. Its next challenge is to establish when those steps remain beneficial through continued use, and when improving the learning process repays the work required to change it.
