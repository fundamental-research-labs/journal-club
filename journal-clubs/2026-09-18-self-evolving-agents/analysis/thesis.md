# Self-evolving agents: what experience makes possible

## Turning completed work into future capability

An agent's work could be valuable twice: for the task it completes and for what the experience teaches it to do next time. A difficult task might reveal a reusable procedure, reducing trial and error on later work. In *Lifelong Learning: A Case Study* (1995), Sebastian Thrun framed earlier tasks as a source of learned assumptions that help a learner generalize from less data on a new, related task. The attraction is cumulative expertise: each task can contribute to a starting point that would have been expensive to construct beforehand. [Thrun, §§1–2](https://www.ri.cmu.edu/pub_files/pub1/thrun_sebastian_1995_1/thrun_sebastian_1995_1.pdf).

Accumulating expertise requires both adaptation and retention. Learning a new procedure can damage an old one, while preserving everything can obstruct useful change. Continual-learning research calls this the stability–plasticity problem. It also distinguishes help on future tasks from changes in performance on earlier tasks. Those questions apply to an agent even when its model weights stay frozen: new instructions, memories, and software can change the complete system's behavior. The unit that learns is then the model together with the state and procedures it uses. [Gradient Episodic Memory, §§1–3](https://papers.neurips.cc/paper/2017/file/f87522788a2be2d171666752f97ddebb-Paper.pdf); [ExpeL, §3](https://arxiv.org/abs/2308.10144v3).

What makes an update self-directed is which decisions the agent controls. Proposing a change, evaluating it, accepting it, and retaining it are different responsibilities. A task agent may acquire an agent skill—a reusable package of instructions, scripts, and supporting resources—through a separate agent that develops it. A production training pipeline may use stronger models and human annotation. Following the whole learning system makes these arrangements intelligible without assuming that the task agent performs every step. It also distinguishes developing a better agent before deployment from learning through subsequent use. [WikiSkill, §§2–3](https://arxiv.org/abs/2608.27454v1).

The evidence supports a practical, conditional account of this ambition. Agents can learn from experience by updating memory, agent skills, prompts, code, or model weights. Whether those updates are worthwhile depends on the expertise already available, how often later tasks benefit, and the cost of learning and inference. Whether their value lasts depends on selecting relevant memory and skills, preserving earlier capabilities, and learning from reliable feedback. These conditions help explain both successful reuse and disappointing results. Meta-learning—learning how to learn—is a further possibility; useful adaptation already matters before improvement in the learning process itself is established.

## From traces to agent skills

An agent trace captures a run: the sequence of actions, tool outputs, and responses. To help with another task, it must support a decision about what to do next. ExpeL made this distinction concrete by extracting natural-language insights from trial-and-error trajectories and retrieving successful trajectories as examples for unseen tasks, while leaving model weights fixed. Experience becomes useful through the insights and examples added to the agent's context. [ExpeL, §§3–4](https://arxiv.org/abs/2308.10144v3).

WikiSkill develops this idea by separating traces, a persistent knowledge base, and agent skills. The task agent generates traces as it works. A maintainer consolidates patterns from those traces into a wiki. A proposer consults the wiki and original traces to create or revise an agent skill. Performance on validation tasks determines whether the candidate replaces the active skill. The task agent receives the skills directly, while the agents developing them consult the wiki. [WikiSkill, §§2–3 and Figure 2](https://arxiv.org/abs/2608.27454v1).

This separation lets the system roll back a skill update without erasing everything learned while developing it. WikiSkill retains the wiki even when it rejects a proposed skill. SkillOpt already preserves rejected-edit feedback, so the distinctive choice is the separately maintained knowledge base, rather than the mere ability to remember a failed change. It creates two different retention decisions: which skill to use now, and which knowledge should inform future proposals. Validation tests the first directly; comparing retained versus removed wiki entries from rejected proposals would test the second. [WikiSkill, §3](https://arxiv.org/abs/2608.27454v1); [SkillOpt, §§3.5–3.6](https://arxiv.org/html/2605.23904v2).

For Qwen-3.5-9B, WikiSkill raises average accuracy across five equally weighted benchmarks from 29.9% without skills to 47.4%. EvoSkill, which uses failure analysis to build reusable skills, reaches 42.3% in the same comparison. The 17.5-percentage-point gain over no skills establishes the value of the resulting skill-equipped system; the 5.1-point margin over EvoSkill measures its advantage over an existing evolution method. Neither comparison isolates the wiki alone. With three evolution runs, separate development and test data, and small validation sets, this is bounded evidence that organizing experience can produce useful agent skills for unseen tasks. Benefits vary: a smaller model gets worse on OfficeQA. Supplying all skills directly leaves their selection from a growing library as a separate problem. [WikiSkill, Table 1 and Appendix B](https://arxiv.org/abs/2608.27454v1); [EvoSkill, §2](https://arxiv.org/abs/2603.02766v1).

Experience can also change model weights. SEAL learns a policy for generating synthetic training data: it writes training content from a passage, the model is fine-tuned on that content, and performance after fine-tuning supplies feedback for the generation policy. In its single-passage experiment, the learned generator yields 47.0% accuracy versus 39.7% for synthetic data generated without learning that policy, over 974 questions from 200 held-out passages. This comparison locates the benefit in learning how to generate training data. It also changes the retention problem: an external skill can be replaced as an artifact, whereas subsequent weight updates can alter knowledge already encoded in the model. SEAL's sequential experiments show such forgetting. [SEAL, §3, Table 2, Figure 6 and Appendix B](https://arxiv.org/abs/2506.10943v2).

These examples identify a design choice with consequences: what should experience change, and how can an unsuccessful change be detected and reversed? Validation is useful only to the extent that its feedback predicts behavior we care about. Before asking how to preserve improvements, however, we need to establish that learning adds value over the alternatives already available.

## When is learning worth the effort?

An agent might receive a curated skill at the outset, learn a skill through experience, or use more test-time compute to solve each task. These investments can all improve answers. Their relative value depends on what the agent starts with and how much later work can reuse what it learns.

FinEvo-Bench tests learning during use: four frameworks sharing one model encounter 120 financial tasks in three shuffled, interleaved orders. Retaining experience improves rubric scores by 9.33–19.37 points over paired resets. Related procedures recur among intervening tasks; recurrence does not require an unmixed stream. The paper does not report uncertainty across runs for these gains. [FinEvo-Bench, §§4.1–4.3 and Table 3](https://arxiv.org/html/2608.06144v1).

In its Claude Code comparison, a fixed expert skill scores 86.67, updating both memory and skills scores 89.47, and updating skills alone scores 93.71, against 71.58 with reset state. Expert guidance supplies much of the gain, but the strongest adaptive alternative exceeds it by 7.04 points. These are alternative systems, not evidence about adding learning to an expert-initialized agent. [FinEvo-Bench, Table 5](https://arxiv.org/html/2608.06144v1).

The quality advantage carries a recurring expense. Expert skill, full evolution, and skill-only evolution respectively consume 159,200, 765,000, and 615,600 execution-plus-reflection tokens per task. Judge costs are excluded; expert-skill preparation is unpriced. For both evolving systems, reflection consumes most of those tokens. Skill-only evolution scores higher while consuming fewer tokens than full evolution in this comparison. [FinEvo-Bench, §4.1 and Table 5](https://arxiv.org/html/2608.06144v1). Allowing more kinds of updates can increase the work of learning without improving the resulting expertise. These token counts do not establish a dollar cost or tell us what the score improvement is worth to a user.

Curated skills therefore belong in the comparison even when learning succeeds. SkillsBench finds that they help on average, while skills generated in a single attempt perform worse than no skills in three dedicated configurations. Its one-shot condition does not test iterative learning with outcome feedback. It does show why the ability to write a skill is insufficient: both human curation and agent learning must produce guidance the task agent can actually use. [SkillsBench v4, Tables 2 and 6, Appendix D.6](https://arxiv.org/abs/2602.12670v4).

The other investment is test-time compute. An agent's *harness* is the software that orchestrates model calls, prompts, tool use, and execution of the task. *Rethinking the Evaluation of Harness Evolution for Agents* finds that parallel solution sampling beats the tested harness-evolution method when both receive five rollouts, or task attempts. In a separate experiment on 34 tasks excluded from harness development, the evolved harness scores 68.3 against 67.7 for the original. Improving the development score thus did little for these new tasks. Under those conditions, parallel sampling was a stronger investment than the tested harness evolution. [Harness evaluation, Tables 1–3](https://arxiv.org/abs/2607.12227v2).

Repeated use can change that calculation. A harness developed once can spread its development cost across later tasks if it helps on those tasks. Continued reflection, retrieval, and training instead introduce expenses that may recur throughout use. More tasks therefore do not automatically make learning economical: the benefit of applying what was learned must exceed the added operating cost before reuse can recover the initial investment. Learning and extra attempts can also reinforce each other. ReasoningBank combines test-time search with retained lessons, so effort spent exploring answers can become material for future learning. A practical comparison needs a specified workload, the value of better outcomes, and both development and operating costs. [Harness evaluation, §4.4](https://arxiv.org/abs/2607.12227v2); [ReasoningBank, §§3–4](https://arxiv.org/abs/2509.25140v2).

These results establish performance gains in some settings, while leaving their net practical value unresolved. They suggest that experience is a promising investment when it supplies missing expertise that later work repeatedly calls upon. Good initial guidance changes what remains to be learned; a different workload changes which lessons are useful. The next question is therefore how the system decides which past experience belongs in its current work.

## Memory retrieval, skill selection, and forgetting

A financial skill can remain correct yet be irrelevant to the next task, making skill selection the immediate problem. If later learning damages performance on earlier financial tasks, the problem is forgetting. A changed tool interface creates another possibility: the skill no longer works in the current environment. These distinctions matter because improving retrieval or skill selection, protecting earlier capabilities, and updating a skill address different failures.

How memory enters the agent's context changes its exposure to these problems. Dynamic Cheatsheet separates answering from maintaining persistent guidance. Building on that design, Agentic Context Engineering, or ACE, uses a reflector to extract lessons and a curator to make small revisions to a structured playbook. Such revisions aim to preserve detail that a wholesale rewrite might erase. Retrieval-based systems instead select stored experience for the current task. Keeping a playbook available can make useful advice easy to apply; selecting a smaller portion can reduce exposure to unrelated advice. [Dynamic Cheatsheet, §§2.1–2.2](https://arxiv.org/abs/2504.07952v1); [ACE, §3 and Figure 4](https://arxiv.org/html/2510.04618v3).

AgentStream makes that tradeoff visible across six benchmarks with 50 tasks each, three models, five methods, and three task orders. In interleaved streams, the average gain is 0.90 percentage points, with improvements and regressions across configurations. ACE's average gain is positive with isolated task domains and negative when they are interleaved. Retrieval-based ReasoningBank and A-Mem show their largest average gains in the interleaved condition. The methods differ in more than retrieval, so this does not identify retrieval as the cause. It does support treating relevance as a central design question: keeping more experience and benefiting from it are different achievements. [AgentStream, Tables 2, 5–6 and 11–13](https://arxiv.org/html/2608.00155v1).

Relevance also changes over time. Library Drift examines storage, retrieval, and skill retirement, finding that removing skills too aggressively can hurt performance. EvoHarnessBench changes the tools, skills, or specialist agents available alongside the tasks. Together they motivate retaining a skill's applicability conditions and checking whether its dependencies still work, rather than using age alone to decide what to discard. A usable skill library must preserve useful skills while helping the agent avoid obsolete or inappropriate ones. [Library Drift, §§5–7](https://arxiv.org/abs/2605.19576v3); [EvoHarnessBench, §§3–4](https://arxiv.org/abs/2609.04280v2).

Fine-tuning faces the corresponding problem of changing one capability without damaging another. Elastic weight consolidation penalizes changes to weights according to their estimated importance; Gradient Episodic Memory retains examples and constrains new gradients using losses on those memories. Their relevance here is the explicit protection of earlier learning. An agent-level evaluation can adopt the same question even when its changing state is a library or harness: after each update, how does a frozen copy perform on earlier, current, and future task families under fixed tools? Performance before training on a future task measures a different benefit from faster adaptation, which requires learning curves. Changing the tools should be a separate test. [Kirkpatrick et al., §2](https://arxiv.org/abs/1612.00796v2); [Lopez-Paz and Ranzato, §§2–3](https://papers.neurips.cc/paper/2017/file/f87522788a2be2d171666752f97ddebb-Paper.pdf).

FinEvo's positive results and AgentStream's mixed results leave two separate questions: how often does a useful procedure recur, and can the agent select it amid other work? Both benchmarks interleave tasks. Their different outcomes cannot be attributed to mixing alone, and differences in feedback, task construction, and methods could explain the contrast. A discriminating experiment would vary recurrence and mixing separately while holding the model, starting guidance, feedback, and total resource budget fixed. If recurrence helps only when the agent can select relevant experience, that would support the proposed explanation. For now, the engineering implication is to evaluate a memory against the work it will be asked to support: a useful specialist procedure need not help every task to deserve retention.

## Feedback quality in self-training

An agent can retrieve a relevant lesson and still learn the wrong thing from it. This problem becomes especially important in self-training, where a model helps produce the examples used to update its own weights. If the system accepts a mistaken answer as correct, training can reinforce the mistake. How does it decide which answers to trust?

R-Zero builds its own mathematics training set using two models. One proposes problems, and the other—the solver—makes several attempts to solve each problem. The system treats the most frequent answer as correct and uses it to reward the solver during training. It then repeats the process with newly generated problems. This supplies training material without a human-written answer key, but the solver is also supplying the answers it will be trained to match. Several attempts can repeat the same error, turning a mistaken answer into a training target. [R-Zero, §§2.2–2.4](https://arxiv.org/abs/2508.05004v4).

R-Zero initially improves at mathematics, but later training undoes some of that progress. In its two-model experiment, the average math benchmark score reaches 49.12 at training step 45, then falls to 46.52 at step 60. Using another model to check the training answers, the authors find that those answers become less reliable as training proceeds. That makes incorrect feedback a plausible contributor to the decline. But the generated problems also change in difficulty and content, so the experiment does not establish which change caused it. [R-Zero, §3.3, Appendix D, Tables 5–6, and Appendix E](https://arxiv.org/abs/2508.05004v4).

An agent that searches the web must also learn which actions lead to an answer. *Rethinking Continual Experience Internalization* studies how to teach a model to perform those actions without needing advice from past experience in its prompt. The researchers first give a copy of the model general lessons extracted from earlier attempts, selecting relevant advice at each step. This copy acts as a teacher. They then train the student model to imitate the teacher's successful runs while withholding the advice from the student. The intended result is that behavior previously supported by the prompt becomes something the model can do through its updated weights. [Continual Experience Internalization, §§3–5](https://arxiv.org/html/2606.04703v1).

Training on complete, successful teacher runs proved more stable than having the teacher suggest corrections along paths the student had already taken. The final recipe, which used a stronger model to extract the lessons, improved results across three training rounds, although one of the three benchmarks dipped before recovering. This is evidence that repeated training can retain gains with a carefully constructed teaching process; it does not establish that the process will remain stable beyond those three rounds. [Continual Experience Internalization, §5.3–5.4 and Appendix D, Table 4](https://arxiv.org/html/2606.04703v1).

In production, failed user interactions can supply the problems to learn from, but someone still has to produce a better response. Shopify describes this process for Sidekick, its assistant for merchants. Stronger models examine a failed conversation and suggest how to fix it. The system then reruns the conversation from the relevant turn with that instruction, and a separate judging model scores the new attempt. Attempts that pass become training examples; failures go to human annotators for correction. Shopify trains a smaller model on the resulting conversations, including earlier examples alongside new ones. The deployed agent therefore benefits from corrections supplied by a larger system of models and people. Shopify describes the process, but provides no controlled comparison separating its components or showing quality after each training cycle. [Shopify Engineering, “Sidekick's continual learning loop,” August 2026](https://shopify.engineering/sidekicks-continual-learning-loop).

That judging model introduces another question: could the system learn to satisfy the judge without serving the user better? Shopify uses its judge both to select training material and to reward the trained model. If the judge overlooks a recurring error, both stages can reinforce behavior containing that error. Checking the finished agent therefore requires evidence beyond its score from the judge used during training. A separate risk arises when an agent can alter the software that scores it. The Reward Hacking Benchmark checks task correctness independently and records attempts to exploit the evaluation process. Its design illustrates two distinct requirements: protect the evaluator from modification, and check whether the result it rewards actually meets the task's requirements. Reliable learning needs both a useful correction to learn from and a trustworthy way to establish that the correction helped. [Shopify, evaluation and training sections](https://shopify.engineering/sidekicks-continual-learning-loop); [Reward Hacking Benchmark, §§4–6](https://arxiv.org/abs/2605.02964v1).

## Can meta-learning improve the update process?

So far, the system has needed rules for preserving experience, proposing changes, and deciding what to adopt. Experience could also improve those decisions. This extends the potential value of learning: the system may acquire a way to adapt that helps on problems its designers did not anticipate.

Meta-learning already pursues this goal without requiring editable improvement code. MAML learns an initialization from which a few gradient steps work well on a new task. SEAL learns to generate synthetic data for fine-tuning. Both place something learned inside a specified adaptation process. Editing the process's software offers another route, especially when the useful change concerns how the system organizes experiments or proposes agent updates. [MAML, §2 and Algorithm 1](https://proceedings.mlr.press/v70/finn17a/finn17a.pdf); [SEAL, §§2–3](https://arxiv.org/abs/2506.10943v2).

Hyperagents develops this route from the Darwin Gödel Machine, or DGM. In DGM, coding agents modify their implementations and an archive preserves alternative agents as starting points for future changes. Its comparator SICA also maintains an archive, but expands from the best-scoring agent; DGM explores other lineages that may become useful stepping stones. DGM still uses a handcrafted mechanism to generate improvement instructions. Hyperagents places task-solving and improvement code in the same editable implementation, allowing proposed changes to affect how later changes are produced. An outer archive and evaluation process still select which implementations survive. [SICA, §3 and Algorithm 1](https://arxiv.org/abs/2504.15228v2); [DGM, §§2–4](https://arxiv.org/abs/2505.22954v3); [Hyperagents, §3 and Appendix B](https://arxiv.org/abs/2603.19461v1).

The important test is what the developed system can help learn next. Hyperagents transfers implementations developed on paper review and robotics reward design to mathematical grading, then holds their improvement code fixed while generating candidate task agents for 50 iterations. Across five runs, transferred implementations achieve a median held-out score improvement of 0.630, with a reported 95% bootstrap interval of 0.540–0.630; the initial implementation's median is zero. The whole implementation transfers, and the initial task agent has formatting failures, so the experiment does not isolate improvement code from the rest of the starting system. It nevertheless supplies positive evidence that an implementation shaped by earlier work can support useful improvement in a new domain. [Hyperagents, §5.2, Figure 3 and Appendix D](https://arxiv.org/abs/2603.19461v1).

A separate experiment allows the improvement method to keep evolving. After 200 iterations, transferred agents score 0.640 versus 0.610 from the initial implementation, a difference that is not statistically significant across five runs. Thus transfer helps establish useful subsequent learning in the fixed-method experiment, while its added endpoint advantage during continued evolution remains uncertain. To isolate a portable learned improvement method, one could attach original and learned methods to identical task agents and compare what they produce. For a system whose task and improvement abilities develop together, one could compare matched runs that either let newly developed capabilities propose later changes or keep the proposal system frozen while task agents continue to change. These are proposed attribution tests for different claims, not universal requirements that every learning architecture must satisfy. [Hyperagents, §5.3 and Figure 4](https://arxiv.org/abs/2603.19461v1).

A further question is whether improvements repeatedly raise the efficiency of producing the next improvement. That requires measuring multiple cycles against a defined resource budget and task difficulty, rather than inferring acceleration from a higher endpoint. The theoretical *Economics of Recursive Self-Improvement* distinguishes narrow acceleration from broad capability gains and shows how other inputs or component ceilings can interrupt a favorable feedback loop. Its assumptions are not measurements of an agent becoming self-sustaining. This stronger possibility remains open alongside the more immediate achievement of useful learned adaptation. [Economics of Recursive Self-Improvement, §§2.3–2.5](https://arxiv.org/abs/2609.15802v1).

## From completing tasks to getting better at the work

A difficult task can teach an agent something that its original instructions did not contain. The agent may discover a way to use a tool, work out a sequence of steps, or find an error in its approach. If it can turn that experience into guidance for another task, the work leaves the agent better prepared than it was before. The model itself can remain unchanged while the agent built around it learns. [ExpeL, §§3–4](https://arxiv.org/abs/2308.10144v3); [WikiSkill, §§2–3](https://arxiv.org/abs/2608.27454v1).

That makes the agent's history matter. Two agents built from the same model could become useful at different kinds of work because they have learned different things along the way. It also changes the developer's job. Writing good initial instructions remains valuable, but the developer must also decide how the agent will recognize a useful lesson, test it, and correct it later. Those decisions shape what experience teaches. An agent rewarded for a convincing answer may preserve a mistake; one given a reliable correction has a chance to avoid repeating it.

Keeping those lessons useful is harder than collecting them. Advice that helped with one task can distract from another. Learning a new fact can interfere with an old one. A tool can change after the agent has learned how to use it. The studies show each of these difficulties, alongside successful reuse. Their combined lesson is that an agent needs to learn when its past experience applies. It must be able to use a familiar procedure, set it aside, or revise it as the work demands. More stored instructions and more rounds of training do not settle those choices.

Learning how to make these choices is the next ambition. An agent might become better at finding useful changes to itself, allowing experience in one kind of work to help it learn another. The meta-learning results offer early evidence for parts of that process. They leave open how far it can continue and whether each round becomes easier or cheaper. Useful learning already matters before that stronger promise is fulfilled: an agent can handle later work better because of what it did earlier. Whether that improvement justifies the effort must be judged over the work people actually need done, against good supplied instructions and the option of spending more effort on each task. The benefit should reach the person giving the agent its next task: a better result, fewer repeated failures, or less work to get the answer.
